# Mio セキュリティポリシー

Mio とその利用者の安全性向上にご協力いただき、ありがとうございます。この文書では、セキュリティ保守の対象バージョンと脆弱性の報告方法を説明します。

## サポート対象バージョン

セキュリティ保守は **Mio v2.1 から**開始します。

| バージョン | セキュリティサポート |
| --- | --- |
| Mio v2.1 | 積極的な保守が行われている間は対象 |
| Mio v2.2 以降 | リリース済みで、積極的に保守されている間は対象 |
| Mio v2.0 以前 | 対象外 |

セキュリティ修正は現在保守中のバージョンを優先します。以前のサポート対象リリースへの修正のバックポートは、深刻度、互換性、保守リソースに応じて個別に判断します。サポートは無期限ではなく、リリースの保守状況が変わった際にはこの表を更新します。

## 脆弱性の報告

Mio は **GitHub Private Vulnerability Reporting** を使用します。リポジトリの [Security Advisories](https://github.com/mio-kobo/mio/security/advisories) を開き、**Report a vulnerability** を選んで非公開で報告してください。

**未修正の脆弱性の詳細を、公開 Issue、Pull Request、Discussions に投稿しないでください。**

可能な範囲で、以下の情報を添えてください。

- 影響を受ける Mio のバージョンまたはコミット SHA。
- OS と CPU アーキテクチャ。
- 問題の概要と想定されるセキュリティ上の影響。
- 再現手順と最小の検証コード（あれば）。
- 関連ログ、診断結果、回避策（あれば）。

実際のパスワード、アクセストークン、機密性のある個人情報は添付しないでください。セキュリティ上の影響があるか判断できないバグでも、非公開で報告して構いません。

## 対象となる問題

以下のような問題が対象になります（これらに限りません）。

- 細工された入力をコンパイラが処理した際の意図しないコード実行やメモリ破壊。
- コンパイラ、ランタイム、GC、Bunko 標準ライブラリにおけるメモリ安全性の問題。
- 意図しないファイルアクセス、情報漏えい、権限昇格。
- ビルド・インストール・配布物の完全性を損なう問題。
- 実際にセキュリティ上の影響を持つサービス拒否（DoS）。

Mio の型システム、GC、ネイティブコンパイルは、**OS レベルのセキュリティサンドボックスではありません**。信頼できないプログラムを動かす際は、OS 側で適切な権限設定と隔離を行ってください。ただし、コンパイラやランタイムが信頼できない入力を処理することで発生する脆弱性は報告対象です。

## 対応と情報公開

メンテナーは、報告の再現、影響評価、修正または緩和策の検討、必要に応じた情報公開の調整に努めます。応答・修正にかかる時間は深刻度、複雑さ、保守リソースによって異なり、**固定の応答期限や解決期限は保証しません**。

Mio は協調的な脆弱性開示（Coordinated Vulnerability Disclosure）を推奨します。悪用の詳細を公開する前に、調査と修正のための時間を設けてください。報告者との連絡には GitHub の非公開セキュリティアドバイザリを使用します。

報告者の同意があれば、研究者として公開謝辞に記載できます。匿名を希望する場合はその意思を尊重します。
