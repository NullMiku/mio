# Mio への貢献

バグ報告、ドキュメントの修正、テストの追加、Bunko 標準ライブラリの拡張、コンパイラの最適化、他プラットフォームへの移植、アーキテクチャの提案を歓迎します。バグ報告には、最小再現例、Mio のバージョン、OS とアーキテクチャ、期待する動作、実際の出力を添えてください。

## 運営方針と設計

Mio は **メンテナー主導（Maintainer-led Governance）**で運営します。コントリビューターは設計を提案し、議論に参加し、実装を提出できます。言語設計、技術方針、PR のマージに関する最終判断はメンテナーが行います。メンテナーは、明確で合理的かつ敬意あるレビューと判断理由の説明に努めます。提案の不採用は、提案者の技術力を否定するものではありません。

レビューでは、言語設計の一貫性、長期的な保守性、アーキテクチャの整合性を重視します。現在の方向性は、ネイティブ AOT、セルフホスト、明確で厳格な型システム、モジュール化された構成です。コアの複雑さを抑え、ABI、ランタイム、GC、プラットフォーム互換性に関わる変更は慎重に扱ってください。一つの機能のために不必要な全体的複雑性を増やさないようにします。これらは探索の指針であり、将来の別案を排除するものではありません。

## 貢献を始める

GitHub でリポジトリを Fork し、自分の Fork をクローンして、対象の開発ブランチから作業用ブランチを作成してください。変更後は対応する上流ブランチへ PR を開き、テンプレートを記入します。以下の Fork 名とブランチ名は例です。

```bash
git clone https://github.com/YOUR-NAME/mio.git
cd mio
git switch -c fix/topic
```

このブランチは `Mio-2.1` です。正式なソースビルドは既存の信頼済み Native Seed と Mio のセルフホスト構成を使用します。macOS ARM64 でのコマンド形式は次のとおりです。

```bash
"$MIO_NATIVE_SEED" build selfhost/cli --bunko-root "$PWD/bunko" -o /absolute/new/path/mio
```

信頼済み Seed のバージョンおよび SHA-256 の取り決めはテスト資料を参照してください。Go（バージョンは `go.mod` 参照）は参照フロントエンド／VM、補助テスト、信頼済み Seed がない場合の go-hosted Stage A の生成にのみ使用します。Go プログラムからネイティブコードを生成することはなく、Go 製 AOT バックエンドは削除されています。共通のテストドライバーは Bash、Python 3.9 以降、Git を使用し、ネイティブ署名の確認には macOS の `codesign` を使用します。これらは Mio の正式配布物の新たな依存関係ではありません。

日常的なコマンド：

```bash
bash scripts/ci/selftest.sh
# 信頼済み Seed がある Apple Silicon Mac の場合：
bash scripts/ci/run.sh macos-arm64 all quick
# Linux では補助的な参照実装のみを実行。
# この結果はネイティブの受け入れ検証の代わりにはなりません：
bash scripts/ci/run.sh linux-amd64 go-reference quick
```

コマンドの対象範囲と実際の結果については [テスト資料](testing.md) と [監査記録](testing-audit.md) を参照してください。現行の監査で使用した実装環境は Windows です。実行していないプラットフォームのコマンドを合格扱いにはしません。

## 事前相談が望ましい変更

言語構文、型システム、コアランタイム、GC、ABI、コンパイラの主要アーキテクチャ、新しいバックエンド、大規模な依存関係の変更は、先に Issue で相談することを勧めます。問題、代案、互換性への影響、検証方法を説明してください。事前の議論は方向性の不一致による手戻りを減らすためであり、技術的な実験や探索は歓迎します。

## コミットと PR の範囲

既存の履歴では `feat(bootstrap): ...`、`fix(aot): ...`、`docs: ...`、`chore: ...` などの簡潔なプレフィックスを使用しています。`feat`、`fix`、`test`、`docs`、`refactor`、`ci`、`chore` を使い、必要なら scope を付けてください。何を、なぜ変更したかを具体的に書きます。中国語でも英語でも構いません。命名のためだけに履歴を書き直す必要はありません。

各コミットはレビュー可能な一つの論理的単位にしてください。無関係な修正、大規模なリファクタリング、機能追加は PR を分け、関連するテストと文書は実装に合わせて提出してください。無関係な整形、生成物、個人設定、別件のコード変更を混ぜないでください。

## テストの根拠

**Mio のネイティブテストフレームワークを主要なテスト手段とします。外部ツールと他言語は、補助テストおよび独立した相互検証にのみ使用できます。**

通常のモジュール、標準ライブラリ、Core／AOT／GC では、まず Mio で書かれたテストを優先し、重要な機能は別の方法でも検証してください。ネイティブ側と独立検証側の結果は分けて記録します。フレームワークが未対応のテスト種別は、その制限を説明してから補助ツールを使用します。他言語で書かれたテストツールは正式実装の一部にはなりません。

独立してテスト可能なモジュールには、専用の `test.sh` と隣接する `ci-module.json` を用意してください。独立入口のない既存パッケージはテスト資料に記録されており、新しいモジュールはこのインターフェースに従います。環境確認、ログ、レポートの共通処理を再利用し、テスト基盤全体を複製しないでください。

コード PR には、実際に実行したコマンド、対象プラットフォーム、結果、ログを記載してください。`PASS / FAIL / SKIP / NOT_RUN` を区別し、スキップ理由も説明します。未実行、空のテスト、クロスコンパイルのみを「合格」と報告してはいけません。

新機能には原則としてテストを追加し、バグ修正には可能な限り回帰テストを添えてください。コンパイラ、コード生成、AOT、ABI、ランタイム、GC、セルフホストなどの重要経路には、正式なテストと独立した結果判定の両方が必要です。`mio test` をもう一度実行するだけでは独立検証になりません。テスト基盤にも負例のセルフチェックを設け、意図的な誤りが非ゼロの終了コードになることを確認してください。

## 外部ツールと Core の分離

Go、Shell、Python などの外部ツールは、補助検証、証拠収集、テスト基盤のセルフチェックに限り **Development / CI Dependencies** として使用できます。それらから Mio を呼び出すことはできますが、Mio Core、標準ライブラリ、正式コンパイラから逆にインポート・リンク・実行してはいけません。新しいテスト依存関係を正式ソースビルド、実行、セルフホストに組み込まないでください。

正式リリースのアーカイブにはテストドライバーとその専用依存関係を含めません。既存の `tools/native-ci` は Mio 製です。製品ビルドは空の PATH、既存の実行サンドボックス、信頼済み Native Seed を維持し、新しい `scripts/ci` はサンドボックス外で動作します。パッケージングを変更する PR では、ソース依存関係の確認、実際のアーカイブ内容一覧、テストツールがない環境でのビルド・実行結果を提示してください。実行できないリリースチェックは `NOT_RUN` と記録します。

過去から存在する Go のブートストラップ／参照実装と、今回追加するテスト専用ツールの依存関係は区別して説明してください。テストの都合で既存のネイティブ Mio Seed ビルド構成を置き換えたり、テストツールをリリースに含めたりしないでください。

## レビュー基準

メンテナーは、正しさ、回帰リスク、アーキテクチャとの整合性、性能、プラットフォーム互換性、テストの十分性、保守性、文書、長期方針を総合的に評価します。**テストの合格はマージを判断する重要な根拠ですが、自動的にマージを保証するものではありません。** 既存の失敗や既知の制限は正直に報告し、重要なチェックの削除、期待値の緩和、テストのスキップによって失敗を隠さないでください。

AI による開発支援は利用できます。PR では使用の有無を明記してください。提出者は変更内容を理解し、正確性、安全性、ライセンスへの適合性、テスト結果に責任を持ちます。AI が生成したテスト報告書は実際の実行証拠の代わりにはなりません。

## CI V2 のテスト入口

通常の PR では `ci-pr.yml` が保守的な Quick プランを作り、`bash scripts/ci/run.sh <target> <modules> quick` を呼び出します。`Mio-2.1` への push、手動実行、定期 Full 実行では `ci-full.yml` が同じ入口に `all full` を渡します。単一モジュールの場合はそのモジュールの `test.sh <target> [quick|full]` も実行できます。正式リリースのワークフローは別のままです。

ネイティブテストでは、まず信頼済み Seed から現在の作業ツリーのコンパイラをビルドし、生成物を再利用してモジュールを実行します。Seed に組み込まれた過去の実装だけを動かしても、現在のソースが合格したことにはなりません。新しい独立モジュールには、隣接する `ci-module.json`、`test.sh`、実際の Mio テストを用意し、重要なモジュールには固定出力・バイト列・終了コード・参照実装などの oracle も用意してください。共通の `ci_native_and_crosscheck` はネイティブ側の失敗後も独立側の証拠を収集できますが、最終終了コードは非ゼロのままにします。

検証資料にはコマンド、プラットフォーム、`report.json` を添え、`PASS / FAIL / SKIP / NOT_RUN` を区別してください。全件スキップや空のチェックを成功と呼ばないでください。CI 基盤の変更では `bash scripts/ci/selftest.sh` を実行し、ワークフローの構文を確認します。既知の Core の失敗を期待値の変更、アサーションの緩和、テストの省略で隠さないでください。[テスト構成](testing.md) と [監査](testing-audit.md) を参照してください。

コンパイラ、バックエンド、ランタイム、GC の変更では、`.github/workflows/native.yml` の 3 プラットフォームのネイティブ検証（`Native / required`）を通過する必要があります。[Runtime ABI 契約](runtime-abi.md) の変更時は `tests/runtime-abi` も更新してください。通常の標準ライブラリテストファイルだけを局所的に変更した場合に限り Quick の対象を縮小できます。実装コード、Core／ABI／GC／AOT、マニフェスト、対象不明の変更は完全な Quick に戻します。macOS は現在 GitHub-hosted `macos-15` を使用しています。

**暫定措置：** 信頼済み Native Seed が GitHub-hosted Runner ではまだ利用できないため、Native Verification は現在 `NOT_RUN` です。リポジトリ変数 `MIO_NATIVE_VERIFICATION=enabled` を設定し、Seed を提供した場合にのみ再開します。`Mio CI / required` の合格は現時点では補助テストの gate に過ぎず、ネイティブ検証の合格を意味しません。[テスト構成](testing.md) と [3 段階 CI スケジューリング監査](ci-scheduling-audit.md) を参照してください。
