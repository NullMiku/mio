# Mio 安全政策

感谢你帮助提高 Mio 及其使用者的安全性。本文说明哪些版本接受安全维护，以及如何报告潜在漏洞。

## 受支持版本

Mio **从 v2.1 开始**提供安全维护。

| 版本 | 安全维护状态 |
| --- | --- |
| Mio v2.1 | 处于活跃维护期时提供支持 |
| Mio v2.2 及后续版本 | 发布且处于活跃维护期时提供支持 |
| Mio v2.0 及以前版本 | 不提供支持 |

安全修复优先进入当前活跃维护的版本。是否向较旧的受支持版本回移补丁，会根据严重程度、兼容性和可用维护资源决定。版本支持并非永久承诺；随着发行版维护状态变化，本表也会更新。

## 报告安全漏洞

Mio 使用 **GitHub Private Vulnerability Reporting（私密漏洞报告）**。请打开仓库的 [Security Advisories](https://github.com/mio-kobo/mio/security/advisories) 页面，选择 **Report a vulnerability**。

**请勿在公开 Issue、Pull Request 或 Discussions 中披露尚未修复漏洞的细节。**

报告中请尽可能提供：

- 受影响的 Mio 版本或 Commit SHA。
- 操作系统及处理器架构。
- 问题描述及可能造成的安全影响。
- 复现步骤与最小测试代码（如有）。
- 相关日志、诊断输出或可行的缓解方法。

请勿附带真实密码、访问令牌或敏感个人信息。如果暂时无法判断一个 Bug 是否具有安全影响，也可以先私密报告。

## 安全问题范围

可能的安全问题包括但不限于：

- 编译器处理特制输入时发生非预期代码执行或内存破坏。
- 编译器、运行时、垃圾回收器或 Bunko 标准库中的内存安全缺陷。
- 非预期文件访问、数据泄露或权限提升。
- 构建、安装或发行产物完整性受到破坏。
- 具有实际安全影响的拒绝服务问题。

Mio 的类型系统、GC 和原生编译机制**不构成操作系统级安全沙箱**。运行不可信程序时，请使用适当的系统权限限制和隔离手段。这不意味着编译器或运行时处理不可信输入时出现的漏洞会被排除在报告范围之外。

## 处理与披露

维护者会尽力复现报告、评估影响、研究修复或缓解方法，并在适当情况下协调披露。响应与修复时间取决于严重程度、问题复杂度和维护资源；**目前不承诺固定的响应或修复时限**。

Mio 鼓励协调漏洞披露。请在公开利用细节之前，为调查和修复留出合理时间。安全报告相关沟通通过 GitHub 私密安全公告系统进行。

经报告者同意后，可公开致谢安全研究者；希望匿名的报告者，其意愿将得到尊重。
