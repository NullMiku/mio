# E5 — 真实 Concurrent Sweep、Allocator/LOS 生命周期安全

**前置门禁**：E4 PASS。不要把 ConcurrentMark PASS 当成内存可在并发期直接释放。

## 1. 资源/对象所有权模型

- 对 Old allocator free bins、对象 Header/Side Metadata、年龄/代际标志、LOS 链表、GC worker、Mutator 所持引用建立 owner/synchronization 表。
- 实现线程安全对象清除与复用。使用 epoch/quarantine、分配器安全点/标记所有权或其他有证明的协议，保证不会被正在读/写的 Mutator 或扫查线程访问；若采用非锁算法，覆盖 ABA 与 memory reclamation 风险。
- 不移动对象，不以 compact/copy 规避；符合原有 16B header、Side Metadata 和 LOS ABI。

## 2. Concurrent Sweep 真正运行

- Sweeper 独立线程在合理安全阶段执行 Old 对象回收时，至少一个真实 Mutator 继续取得进展并安全进行对象操作；用有起止时间的真实 trace 证明重叠。
- 尚不可回收的对象必须保留；任务取消/Abort/线程退出/GC 再入时不会同时被两个 Sweeper 领取。
- 各 free bins 和分配器之间的同步不能引入无界等待；观察 swept/unreclaimed/quarantine 数量和释放延迟。

## 3. LOS 的安全释放

- 解绑、回收与真实 `munmap` 必须考虑所有 Reader 和线程 epoch。生命期尚在的 LOS 不能提前释放；死亡但有读者访问风险的映射进入 quarantine。
- `munmap` 返回失败时保留映射和 owner 记录，允许之后安全重试；不能让已失败的映射消失于 accounting。
- 与旧 LOS 单次有界释放和堆费用计量语义兼容（对新的并发/延迟策略需明确记录版本化差异）。

## 4. 与 Minor / 晋升 / OOM 交错

- Old Sweep 期间的 Young Minor、晋升 Old、Old→Young remembered list、LOS 和 heap pressure 必须严格协调。
- OOM / Hard Cap / 堆损坏应报告明确错误，而不是吞错继续访问已清除内存。Worker 失败要停止进一步不安全 reclaim。
- Shutdown 必须 join GC worker 或完成可证明的终止交接，释放归属清楚；不能让 OS 线程在 Runtime 元数据销毁后仍操作它。
